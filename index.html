What you need

  • A GitHub account (free)
  • A domain whose DNS you can edit — this guide uses a web3 domain, and section 05 covers what makes those different

Why bother with plain files?

Because there’s nothing to break. No framework to update, no dependency that disappears, no runtime to patch. Your site is a folder that still opens in ten years — and if you ever want to leave, you drag the folder somewhere else.

01

Write the files

5 min

Make a folder called mysite and put these inside. This very page is built exactly this way.

mysite/
├── index.html      the page itself (required)
├── favicon.svg     the little tab icon
├── .nojekyll       empty file - see below
└── CNAME           added in step 04, your domain only

index.html

GitHub Pages serves index.html at the root automatically. This one keeps everything inline — no separate stylesheet, no JavaScript, nothing to break.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>My site</title>
  <style>
    body { font-family: system-ui; margin: 0; }
    .wrap { max-width: 900px; margin: auto; padding: 24px; }
  </style>
</head>
<body>
  <div class="wrap">
    <h1>It works.</h1>
    <p>Served from GitHub Pages.</p>
  </div>
</body>
</html>

The .nojekyll file

Create a completely empty file called .nojekyll, with no extension and nothing inside it. GitHub runs Pages through a system called Jekyll, and Jekyll silently skips any folder whose name starts with an underscore. This file turns Jekyll off so every file and folder you commit gets published exactly as-is.

Do this before your first push

If you leave it out you’ll lose an afternoon. A file you can plainly see in your repo simply won’t appear on the site, with no error message anywhere. If that ever happens, this file is the first thing to check.

02

Create the repo and upload

5 min

Create it

  1. Open github.com/new
  2. Type the folder name into the repository name box
  3. Choose Public — Pages on a private repo is a paid feature
  4. Click Create repository
  1. 1Repository name becomes your address: username.github.io/<this-name>. Keep it short.
  2. 2Description — optional, but it’s what visitors see first.
  3. 3Public. Required for free Pages. Then Create repository.

Upload

Drag your files onto the empty repo, or click choose your files. Then scroll down and Commit changes.

The name has to be exactly right

myfile.html gets you a 404. GitHub only serves the root automatically for the exact lowercase name index.html.

Or use the command line

Faster once you’re past the first commit, and you get proper history:

git init -b main
git add .
git commit -m "Add site"
git remote add origin https://github.com/username/repo.git
git push -u origin main
Never leave a token in a remote URL

A URL like https://user:token@github.com/… is written in plain text to .git/config and into your shell history. If you must, push and then immediately reset it: git remote set-url origin https://github.com/username/repo.git.

03

Switch on GitHub Pages

3 min

In your repo open Settings → Pages.

  1. 1The green box — your proof it worked. Copy that URL; test it before touching DNS.
  2. 2Source: Deploy from a branch, branch main, folder / (root). These three are all that matter.
  3. 3Custom domain, further down. Step 04.
Test the github.io URL right now

Open username.github.io/<repo>/ and confirm your site renders. If it does, GitHub is working perfectly and anything that fails later is DNS — not Pages. Knowing which half is broken saves a lot of time.

04

Point the domain at GitHub

10 min

Two pieces of setup, and the order matters.

4a — the CNAME file

Create a file named exactly CNAME containing one line and nothing else:

hostingguide.virtualsociety
This one file controls your Pages URL

The moment CNAME exists, GitHub redirects username.github.io/<repo>/ to your domain with a real HTTP 301, on the server — not with JavaScript. If your domain isn’t working yet, every visitor to your Pages URL gets sent to a broken page and the Pages URL becomes unusable.

That’s fine — just don’t be surprised. If you need to undo it, rename the file to CNAME.disabled, commit, and GitHub goes straight back to serving the Pages URL. Rename it back when the domain is live.

4b — the DNS records

Add these at your domain provider:

typenamevalueTTL
A@185.199.108.153300
A@185.199.109.153300
A@185.199.110.153300
A@185.199.111.153300
CNAMEwwwusername.github.io300

GitHub uses four anycast addresses. Add all four — they cost nothing, and they keep the site reachable if any single address is ever withdrawn. Note each one is its own row; you can’t put four addresses in one record.

The value people get wrong

The www CNAME must be your username’s Pages host — username.github.io, never username.github.io/myrepo. The A records are the opposite: they’re GitHub’s, the same for every Pages site on the internet, and unrelated to your account.

  1. 1Status line. “not resolving” here is normal before you sign — it flips once the chain catches up.
  2. 2Wallet Address — the wallet registered to this domain. This is the account that signs your records.
  3. 3Sign Transaction appears here once a wallet is connected. This button is the whole game on a web3 domain — everything below it is just configuration until you press it.
  4. 4Forward Domain — the trap. Its own caption admits it “will disable your root A record”. Leave it off.
  5. 5The A row on 185.199.108.153. This is the record that points your domain at GitHub.
  6. 6The CNAME handling www. The two NS rows come with the domain.
Forward Domain is not what you want

That toggle says “Will disable your root A record pointing to 185.199.108.153”. Switch it on and your domain stops pointing at GitHub altogether — it forwards somewhere else instead, and your site never loads. It’s for domains you want to redirect elsewhere: one for sale, an old brand pointing at a new one. Not for hosting.

4c — don’t let the records get stuck

Almost every “my domain doesn’t resolve” problem on a web3 domain comes down to one of five things. None of them are your fault, all of them are avoidable, and every one of them looks perfectly normal in the dashboard while doing nothing at all. Read this list before you add records.

1. “Stuck” almost always means a dead key, not a slow one

If your domain sits on 34.22.218.54, that’s Freename’s parking page — it means the nameserver found no record it could use. It is not “propagating” and it will not fix itself. Something is wrong with a key. Go to When it goes wrong and work down the list.

the trapwhat you seethe fix
A zone record left pointing at a key that doesn’t exist Record looks perfect, domain parked forever Delete that record and re-add it as a plain A
Capital letters in a record name Row sits in the table doing nothing Lowercase the key — record.A.1, never RECORD.A.1
A record saved but never signed Saved, displayed, still no effect Press Sign Transaction and confirm in your wallet
Using Update instead of delete + re-add Half-written rows, duplicated entries Always delete and re-add. Never edit a record in place.
Waiting under two minutes Looks broken, actually just lagging Give it two minutes. Beyond that it’s a real fault.
The one that catches everyone

A DNS record can carry an internal pointer to an on-chain key. If that pointer names a key you never created — a stray token name, a typo, a leftover from an earlier setup — the nameserver reads it, finds nothing, and parks your domain. The record itself looks flawless.

This is the single most common cause of a stuck web3 domain, and it is invisible in the record table. Fix: delete the record and add it fresh, plain. If it sticks again, check the key name character by character.

Your 60-second health check

After adding records, run this. If it returns your GitHub IP, you’re done. If it returns 34.22.218.54, something above went wrong. 

nslookup -type=A yourdomain.virtualsociety ns1.noto.network
05

Sign the record — web3 only

Critical
Skip this section if your domain is a normal one

Everything below applies only to web3 domains on an alt-root — names ending in .virtualsociety, .hodl, .nfts, .metaverse and similar. If your domain is a conventional .com, section 04 is the end of the line and you’re done.

On a web3 domain your records live on a blockchain, and the nameserver reads them from there. That changes two things, and both surprise people badly.

It looks right but isn’t

The dashboard will happily save a record, display it back to you in a tidy table, and every field will look perfect — while your domain points somewhere else entirely. Saving is not publishing. Until the record reaches the chain, the nameserver has nothing to serve.

One slot per address

Each IP needs its own on-chain slot. Four addresses means four records, not one record with four values:

slotvalue
RECORD.A.0185.199.108.153
RECORD.A.1185.199.109.153
RECORD.A.2185.199.110.153
RECORD.A.3185.199.111.153
REDIRECT.WEBSITE.0https://username.github.io/<repo>/
Capital letters matter

The redirect key is REDIRECT.WEBSITE.0, written in capitals. redirect.website.0 in lowercase is a different record — it will sit in your table looking perfectly reasonable while doing nothing at all. This one cost us hours. If a record isn’t behaving, check its capitalisation first.

Then sign it

Near the top of the same Records tab there’s a Wallet Address box with a Sign Transaction button. That button is what commits your saved records to the chain. Until you press it, you have configuration, not a live domain.

  1. 1RECORD.A.0 → 185.199.108.153. One slot, one address.
  2. 2RECORD.A.1 → 185.199.109.153
  3. 3RECORD.A.2 → 185.199.110.153
  4. 4RECORD.A.3 → 185.199.111.153
  5. 5REDIRECT.WEBSITE.0 → your Pages URL. Capital letters.
What “correct” looks like

In DNS Records you should see an A row on 185.199.108.153 plus the two NS rows and your www CNAME. In Web3 Records you should see exactly five rows: RECORD.A.0 through RECORD.A.3 holding the four GitHub IPs, and REDIRECT.WEBSITE.0 holding your Pages URL. Then press Sign Transaction.

The order that works

Save the records → sign the transaction → wait for the nameserver to pick it up. Nothing in step 04 will appear to work until step 05 is done, and no amount of waiting will fix it. This ordering is the single most common reason a web3 domain that looks correctly configured never loads.

06

Verify it works

2 min

Check it resolves

nslookup yourdomain.com ns1.noto.network

You want to see 185.199.108.153.

Do not test a web3 domain with a plain lookup

Ask any public resolver — Google, Cloudflare — about a web3 domain and it will always answer NXDOMAIN. That is correct, not a fault: the name lives on an alt-root, outside the ordinary DNS tree entirely. A public lookup tells you nothing about whether your setup is right, and can make a perfectly working domain look broken. Always query the alt-root’s own nameserver.

Then read the result

what you seewhat it means
Your siteDone.
404 from GitHubDNS is fine; the repo isn’t serving. Check the filename is exactly index.html.
Old host or a 502Your domain still points at whatever it pointed at before. The change hasn’t propagated — or was never signed.
Nothing at allNameservers are wrong, or the record was never committed to the chain.
About waiting

Changes can take minutes or hours depending on your provider and the previous record’s TTL. If the lookup shows the right IP but the page still errors, give it time and reload. If it shows the wrong IP, waiting will never help — the records aren’t signed or aren’t set.

!!

When it goes wrong

Keep this

My domain is stuck on the parking page

If nslookup returns 34.22.218.54, your domain is on Freename’s parking page and it will not fix itself. That address means the nameserver found no usable record. Work down this list:

  • Delete and re-add your A record. Do this first, every time. A zone record can carry an internal pointer to an on-chain key that doesn’t exist, and only re-adding clears it.
  • Check the key name on every record, letter by letter. A typo or a leftover token name is invisible in the table.
  • Make sure it’s signed. Unsigned records display perfectly and do nothing.
  • Check capitalisation — record.A.1 works, RECORD.A.1 does not.
  • Then wait two minutes. Only now. Under two minutes it’s propagation; past two minutes it’s a fault.

My Pages URL redirects to a dead domain

That’s the CNAME file doing exactly its job — GitHub 301s the Pages URL to your custom domain. If the domain isn’t live yet, rename CNAME to CNAME.disabled and commit. Rename it back once the domain works.

Records look perfect but the domain points elsewhere

On a web3 domain this is almost always the chain, not a typo. The dashboard and the nameserver read from different places and only one is authoritative. Confirm each address sits in its own RECORD.A.* slot, then press Sign Transaction.

I spelled the redirect key in lowercase

It saved, and it looks fine, and it does nothing. REDIRECT.WEBSITE.0 is capitalised; the lowercase spelling is a different record. Delete it and create it again in capitals.

Editing a record broke it

Changing an existing record in place sometimes leaves it without a valid chain slot, so it stops being served. If an edit doesn’t take effect, delete the record and create it fresh rather than editing it a second time.

A file I committed isn’t showing up

You didn’t create .nojekyll. Add the empty file and commit — no restart needed.

GitHub says “the certificate does not exist yet”

That’s Enforce HTTPS being refused, and for a web3 domain it is permanent. Those domains are HTTP-only — no certificate can be issued. Leave the box unticked and carry on; nothing is broken, and your site will simply be reached over http://.

A public resolver says my domain doesn’t exist

Expected, and harmless. Web3 domains aren’t in the ordinary DNS tree, so public resolvers always return NXDOMAIN. Query ns1.noto.network instead.

www and the bare domain behave differently

Normal for a few minutes — the A records and the CNAME propagate separately. Once both settle they serve the same site, because GitHub treats both hostnames as yours via the CNAME file.
