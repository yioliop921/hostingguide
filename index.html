1

How this actually works

Read first

You have three moving parts. GitHub holds and serves the files. Your domain tells the world where they are. A third thing — the redirect — is what makes a web3 domain usable in an ordinary browser.

partwho uses itwhat it holds
DNS zone recordNormal DNS lookupsOne IP: 185.199.108.153
On-chain recordsWeb3 browsersThe same one IP, plus the redirect
CNAME fileGitHubYour domain, so GitHub answers for it
There are two record layers, and they are not the same thing

A .virtualsociety domain keeps records in two places: a DNS zone and the blockchain. Different software reads different layers. Setting one and not the other is the single most common reason a site “works for me but not for anyone.” You need both, and they must agree.

Which half is broken

Almost every failure is one of three things, and you can name the culprit before you change anything. Check the free .github.io address first: it tells you whether the fault is GitHub or your records.

What you need first

  • A GitHub account
  • Your .virtualsociety domain, in your Freename dashboard
  • One folder of files: index.html, and whatever else you want
2

Build the site on GitHub

10 min

2a — Create the repo

On GitHub, New repository. Name it anything. Set it to Public — Pages on a private repository is a paid feature. Leave Add a README off and .gitignore at None. Create it.

2b — Upload your files

In the empty repo choose uploading an existing file, drag your files in, and commit. Two things matter:

  • index.html must sit at the top level of the repo and be spelled exactly index.html — lowercase. In a subfolder, or spelled Index.html, the site is a 404.
  • Pages publishes the repository as it is, with no build step, so upload only files you are happy for anyone to read.

2c — Turn on Pages

Repo → Settings → Pages → Source: Deploy from a branch, branch main, folder / (root). Save.

Wait for the green check

GitHub builds in about a minute. You can watch it on the Actions tab. Once it finishes, your site is live at https://YOURNAME.github.io/REPO/. Open it and confirm before moving on.

2d — Add the CNAME file

Create a file named exactly CNAME — capital letters, no extension — containing your domain and nothing else: 

yourname.virtualsociety

Commit it to the same branch.

Do not delete this file later

The CNAME is how GitHub knows which site to serve when your domain asks for it. Without it, GitHub answers 404 to your domain even though everything else is configured perfectly. It also makes GitHub redirect the .github.io address to your domain, which looks alarming but is correct and harmless.

Going back to the .github.io address

Rename CNAME to CNAME.disabled and commit, and GitHub serves YOURNAME.github.io/REPO/ again. Remove the file altogether and the custom host simply stops answering — that is the 404 in step 5.

3

Point the domain at it

10 min

Open your domain in Freename → Records. Add these.

3a — DNS records

typenamevalueTTL
A@185.199.108.153300
CNAMEwwwYOURNAME.github.io300
Why only one A record?

GitHub normally asks for four addresses. This zone allows a single apex A, and one is enough — it is the only one we need in either layer. Do not add the other three anywhere; they change nothing and only give you more places to make a mistake.

Leave “Forward Domain” switched off

That toggle says it will disable your root A record. Switch it on and your domain stops pointing at GitHub entirely. It is for domains you want to send somewhere else, not for hosting.

“Enforce HTTPS” will stay unavailable

GitHub only issues a certificate for a domain it can find in the public DNS root, and your name is not in it. The checkbox never becomes usable, no matter how correct your records are. That is the same alt-root limit as step 6.

3b — Web3 (on-chain) records

These are the ones web3 browsers read. Add exactly two:

keyvalue
record.A.0185.199.108.153
redirect.WEBSITE.0https://YOURNAME.github.io/REPO/
Two records is the whole list

One address, one redirect. Adding record.A.1 through record.A.3 is not required and has no effect — this exact pair is what a working setup looks like. If you already added the extra three, delete them; the site keeps working.

Three things that silently do nothing

Capitalisation. The keys are lowercase: record.A.0. Written RECORD.A.0 it saves, appears in your list, and is ignored.
Trailing slashes. The redirect value ends with /. Without it the browser may be sent to a folder listing.
The redirect must be a real URL. Point it at the public .github.io address — never at your own web3 domain, which cannot be reached from the ordinary web.

Adding a record versus changing one

Freename matches a record by its key, so record.A.0 is a row you edit, not a list you append to. A value that is not an address will not work either: keep it a bare IP, with no http:// and no path. The URL belongs in redirect.WEBSITE.0 and nowhere else. After any change, sign again — an unsigned edit is a draft, exactly like the first one.

3c — Sign the transaction

Nothing is live until you do this. Freename will show a Sign Transaction button once your wallet is connected; press it and confirm.

Before you start: avoid the record that breaks everything

If a record ends up carrying an internal pointer to a key that does not exist — a stray name, a typo, a leftover — the domain silently stops resolving and nothing in the dashboard will tell you why. The record looks perfect. If a domain is stuck, delete the record and re-add it clean. It is the first thing to try and it fixes most cases.

Check it works

2 min

Then confirm the site is genuinely being served:

You are finished when all three are true

The nslookup returns your GitHub IP, the curl prints your HTML, and opening https://YOURNAME.github.io/REPO/ in a normal browser shows your site. Alt-root domains have no public DNS and no public certificate, so they will never load in a stock browser — that is expected and is what the redirect exists to work around.

Or check it in a browser, with nothing installed

5

When it doesn’t work

Keep this

Stuck on 34.22.218.54

That is Freename’s parking page. It means the nameserver found no usable record. It will not fix itself. Work down this list:

  1. Delete and re-add the A record. Always first. This clears a bad internal pointer, which is the usual cause and is invisible in the dashboard.
  2. Check every key letter by letter for a typo or a leftover name.
  3. Check capitalisation — lowercase record.A.0.
  4. Confirm you signed the transaction. Unsaved-to-chain records show perfectly and do nothing.
  5. Only then wait two minutes. Under two minutes is propagation. Past two minutes is a fault.
If the same value will not take

Re-saving a value that has not changed can be treated as no change at all. Set the record to GitHub’s second address, 185.199.109.153, sign, wait two minutes, then set it back to 185.199.108.153 and sign again. GitHub answers on any of its four addresses, so if the site comes up while the record holds the second value, leave it there — one working address is the whole requirement.

The record saved but nothing moved

Freename keeps a key exactly as you typed it and matches it literally. A key that looks almost right saves without complaint and is never used:

key you typedwhat happens
record.A.0Correct, and matched
RECORD.A.0Saves, appears in the list, ignored
record.A · A.0Never used
redirect.WEBSITEMissing the .0 — ignored

GitHub returns 404 for your domain

The CNAME file is missing, misspelled, or in the wrong folder. It must sit at the top level of the repo, named CNAME, with no extension.

GitHub says “DNS check unsuccessful”

This is expected. Ignore it. GitHub checks your domain by looking it up in the public DNS root, and an alt-root domain is not in that root — so the check can never succeed, no matter how correct your records are.

Prove it with the nslookup and curl commands in step 4, or the registry’s DNS tool. If those return your GitHub IP and your HTML, the setup is finished and this warning is just noise.

Your Pages address redirects to a dead page

That is the CNAME working correctly — GitHub is sending .github.io traffic to your domain. Nothing is wrong. Ignore it.

Everything looks right and nothing loads

You almost certainly skipped the Sign Transaction step. Saving a record is not publishing it.

6

The one hard limit

Know this

Alt-root domains have no entry in the public DNS root and no public certificate authority, so your domain will never open in an ordinary browser. That is a property of the domain, not a mistake in your setup.

Two consequences worth planning around:

you wantwhat works
A site anyone can open The .github.io address, the registry’s web2 mirror below, or your own normal domain pointed at GitHub
A web3 browser to open it Works, via the redirect you set in step 3b
Both Host in both places, or use the mirror — it needs no second copy of your files

The web2 mirror you already have

Every registered .virtualsociety name is also served on the ordinary web at <name>.virtualsociety.top, over normal HTTPS, from a proxy in front of your GitHub Pages site. There is nothing to configure and nothing to keep in sync. 

https://yourname.virtualsociety.top/

A name that has nothing published yet opens a holding page there instead, which is how you can tell the two apart. Relative links keep working, because the mirror rewrites them; the one thing it cannot rescue is an absolute URL that hard-codes your web3 name.

On Obian specifically

Obian resolves the domain to an IP and then requests that IP on its own, without telling GitHub which site it wants. GitHub cannot answer that — it serves thousands of sites and needs the name to pick one — so you get a 404. No record setting changes this, and the mirror does not either: it is a web2 address, not part of the name itself. If a site must open in Obian, host it somewhere whose IP answers without a hostname, such as Vercel.
